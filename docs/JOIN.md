# 새 PC를 붙이는 `agentctl join` 설계

- 문서 상태: **설계 초안 v0.1 (2026-10-16), 구현 전, 검토 중** (목표 버전 0.5.0)
- 사용자 요구: "새 PC가 받는 PC의 IP와 포트만 알면 연결되는 간단한 구조." 사용자 결정: 확인은 6자리 숫자 하나로 한다. 확인 없는 자동 승인 옵션은 넣지 않는다.

## 1. 사용자가 보는 흐름

```
받는 PC     agentctl pair --open                       참가 요청을 받는 시간을 연다(기본 10분)
새 PC       agentctl join 192.168.75.36:7420           포트는 생략하면 7420. 화면: "확인 숫자 482 913. 받는 PC에서 승인하세요"
받는 PC     "devmain (192.168.75.99)가 참가를 요청했습니다. 새 PC 화면의 6자리 숫자를 입력하세요."
            agentctl pair approve 482913
새 PC       "Connected to desktop-scmain."
```

- 코드 복사가 없고, 새 PC에는 수신 포트도 방화벽 규칙도 필요 없다(접속하는 쪽이므로).
- 기존 `agentctl pair`와 `agentctl pair <코드>`는 그대로 둔다.
- 받는 PC에 요청이 쌓여 있는지는 `agentctl pair pending`으로 본다(호스트 이름, 주소, 경과 시간). **받는 PC는 확인 숫자를 보여 주지 않는다.** 숫자는 새 PC 화면에서 사람이 옮겨 입력하는 것이 확인이다.

## 2. 왜 숫자 확인인가

주소만 알고 접속하는 처음 연결에서는 상대가 진짜 그 PC인지 확인할 방법이 없다. 같은 네트워크의 공격자가 둘 사이에 끼어들면(중간자) 새 PC는 공격자의 인증서를 믿고 토큰을 넘겨주게 된다. 양쪽이 **각자 본 값**으로 같은 숫자를 계산하게 하면, 중간자가 있을 때 두 숫자가 달라서 사람이 승인하지 않는다(블루투스 숫자 비교 페어링과 같은 원리).

## 3. 프로토콜 (기존 TLS WebSocket 위, 인증 전 프레임)

받는 PC H, 새 PC J. `fpH`는 H의 인증서 지문이다(H는 자기 것을 알고, J는 TLS로 본 것을 쓴다).

1. J → H `{t:'join', v:1, host:<J의 호스트 이름>, commit:<SHA-256(nonceJ) 16진수>}`
   H가 요청을 받을 수 없으면(창이 닫힘, 대기 요청이 가득 참, 이름이 이상함) `{t:'error', code}`로 끝낸다.
2. H → J `{t:'join_challenge', v:1, nonce:<nonceH, 무작위 16바이트>}`
3. J → H `{t:'join_reveal', v:1, nonce:<nonceJ>}`. H는 SHA-256(nonceJ)가 `commit`과 같은지 확인한다(다르면 거부, 실패로 센다).
4. 양쪽이 확인 숫자를 계산한다. `SAS = (SHA-256("agentlink-join-v1" ‖ fpH ‖ hostJ ‖ nonceJ ‖ nonceH) 의 처음 8바이트를 정수로 본 값) mod 10^6`을 6자리로 쓴다. J는 이것을 화면에 표시하고 기다린다. H는 표시하지 않는다.
5. 사람이 H에서 `agentctl pair approve <6자리>`를 실행한다. 데몬은 대기 요청 중 SAS가 같은 것을 찾아 승인한다(상수 시간 비교). 맞는 것이 없으면 실패이고 창의 실패 횟수가 1 늘어 5가 되면 창이 닫힌다.
6. 승인되면 H는 무작위 토큰(32바이트)을 만들어 `peers.json`에 `{name:hostJ, token, dial:false}`를 쓰고 같은 소켓으로 `{t:'joined', v:1, host:<H의 이름>, token}`을 보낸다. J는 `{name:hostH, address, port, token, fingerprint:<본 fpH>, dial:true}`를 쓰고 접속을 시작한다. 승인 전에는 양쪽 모두 아무것도 저장하지 않는다.

**중간자가 있을 때:** M이 J와 H 사이에 있으면 J가 본 지문은 M의 인증서 지문이고 H가 가진 것은 진짜 `fpH`라서 두 숫자가 다르다. `commit`이 있어 M은 상대의 nonce를 본 뒤에 자기 nonce를 골라 숫자를 맞출 수 없다. M이 숫자를 맞출 확률은 한 번에 100만분의 1이고 창은 5번의 실패 뒤에 닫힌다.

## 4. 받는 PC의 제한

- 창이 열려 있는 동안에만 `join`을 받는다(기본 10분, 최소 시간은 환경변수로 시험용으로 줄일 수 있다). 창은 `pair approve`로 한 호스트가 승인되면 닫지 않고 시간이 끝날 때까지 열어 두되, `agentctl pair --close`로 닫을 수 있다.
- 대기 요청은 최대 8개, 같은 주소에서 동시에 1개. 요청은 2분 뒤 또는 소켓이 닫히면 사라진다.
- 이미 `peers.json`에 있는 호스트가 다시 요청하면 `known`으로 표시하고, 승인하면 토큰을 새로 만들어 바꾼다.
- 자기 이름과 같은 호스트 이름, 규칙에 맞지 않는 이름은 거부한다.
- 인증 전 연결 수 제한(주소당 4개, 전체 32개)은 그대로 적용된다.
- 이미 승인된 요청이나 닫힌 창에 대한 `join`은 `UNAUTHORIZED`로 거부한다.

## 5. 새 PC의 동작과 오류

- `agentctl join <주소>[:<포트>] [--wait <초>]`: 기본 2분 기다린다. 오래 기다리는 동안 숫자를 표시한다.
- 시간이 지나거나 거부되면 `agentctl`이 이유를 알려 주고, 아무것도 저장하지 않는다.
- 연결이 거부되면(`ECONNREFUSED`) "그 PC에서 `agentctl pair --open`을 실행했는지 확인", 응답이 없으면 방화벽(받는 PC의 TCP 포트)과 주소를 안내한다(`pair`와 같은 구분).
- 받는 PC의 방화벽 규칙은 여전히 필요하다([LAN.md](LAN.md) "방화벽 규칙").

## 6. 위협 모델과 한계

| 위협 | 대응 |
|---|---|
| 같은 네트워크의 아무나 접속 시도 | 창이 열려 있을 때만 받고, 승인은 사람이 새 PC 화면의 숫자를 입력해야 한다. |
| 중간자 | 숫자 불일치(위), commit으로 nonce 조작 방지. |
| 숫자 무작위 대입 | 창당 5번의 실패에서 닫힘. 요청은 짧게 산다. |
| 요청 폭주 | 대기 8개, 주소당 1개, 인증 전 연결 제한. |
| 승인된 PC가 이후에 하는 일 | 다른 연결된 PC와 같다. 접근 제한은 ACL(`agentctl acl init`)이 한다. |
| 사람이 숫자를 대충 입력 | 받는 PC가 숫자를 보여 주지 않으므로 새 PC 화면을 봐야만 입력할 수 있다. 하지만 같은 사람이 양쪽을 다루면 사실상 확인이 약해진다(한계). |
| 새 PC가 가짜 호스트 이름을 댐 | 이름은 자기 주장이다. 승인할 때 보이는 주소(IP)와 이름을 확인한다. 같은 이름이 이미 있으면 `known`으로 표시한다. |

## 7. 시험 계획

1. 정상: 숫자 일치로 승인되고 양쪽 `peers.json`이 쓰이며 링크가 `up`이다(임시 데몬 두 개).
2. 틀린 숫자는 거부되고 5번 뒤 창이 닫힌다. 닫힌 뒤에는 올바른 숫자도 거부된다.
3. 창이 없을 때 `join`은 거부된다. 창이 만료되면 대기 요청이 사라진다.
4. 중간자 시뮬레이션: 인증서가 다른 프록시를 사이에 두면 두 숫자가 다르고, 새 PC에 표시된 숫자로는 승인되지 않는다.
5. commit이 맞지 않는 reveal은 거부된다. 대기 요청 한도, 주소당 한도.
6. `known` 호스트의 재참가는 토큰이 바뀐다. 승인 전에는 어느 쪽에도 `peers.json`이 바뀌지 않는다.
7. 기존 `pair`와 `pair <코드>`가 그대로 동작한다.

## 8. 아직 정하지 않은 것(검토 의견 요청)

- 확인 숫자를 6자리로 충분한가(100만분의 1, 5번 실패에서 닫힘). 8자리로 올릴 만한가.
- 창을 `pair approve` 뒤에 바로 닫을지, 시간이 끝날 때까지 열어 둘지(여러 PC를 연달아 붙이는 경우).
- 받는 PC가 Claude 세션일 때, 요청이 오면 어떻게 사용자에게 알릴지(감시기처럼 깨우는 방식).
