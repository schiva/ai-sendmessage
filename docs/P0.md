# P0: 채널 MCP로 외부 입력을 세션에 주입

- 목표(RFP 10절): 채널 MCP 한 개로 한 PC에서 외부 입력을 세션에 주입한다.
- 완료 기준: 세션이 `<channel>` 메시지에 반응한다.

## 구성

| 파일 | 역할 |
|---|---|
| `src/p0/channel.ts` | 채널 MCP 서버. `claude/channel` capability 선언, `reply` 도구, `127.0.0.1` HTTP 수신(`POST /`)과 SSE 송신(`GET /events`). |
| `src/p0/selftest.ts` | Claude Code 없이 서버 쪽을 검증하는 MCP 클라이언트 테스트. |
| `.mcp.json` | (저장소에는 없음) 아래 절의 내용을 직접 만들어 쓴다. 저장소에 두면 클론한 사람의 Claude가 이 서버를 승인하라고 묻게 되므로 커밋하지 않는다. |

환경 변수: `LANMSG_P0_PORT`(기본 8788), `LANMSG_P0_TOKEN`(없으면 무작위 토큰을 만들어 시작할 때 stderr에 출력한다. 널리 알려진 기본값은 두지 않는다).

`.mcp.json` 예시(이 저장소 루트에 직접 만든다):

```json
{
  "mcpServers": {
    "lanmsg-p0": { "command": "node", "args": ["./src/p0/channel.ts"], "env": { "LANMSG_P0_TOKEN": "<직접 정한 토큰>" } }
  }
}
```

## 검증 상태

| 항목 | 상태 |
|---|---|
| 서버 쪽 자체 테스트(`npm run p0:test`): capability, 도구, 토큰 거부, 본문 크기 제한, 알림 전달, meta, reply 스트리밍 | 통과 (9/9) |
| 실제 Claude Code 세션에서 `<channel>` 주입과 반응 | 차단됨(2026-10-16): 시작 시 `blocked by org policy (server:lanmsg-p0)`. 서버와 HTTP는 정상(`ok` 응답)이지만 Claude Code가 채널 메시지를 조용히 버린다. 이 PC에는 관리형 설정 파일과 정책 레지스트리가 없으므로, 로그인한 계정이 조직(Team/Enterprise 등)에 속해 `channelsEnabled`가 꺼져 있는 것으로 추정된다. |

## 수동 확인 절차

개발 플래그는 대화형 세션에서만 동작하고 확인 대화상자가 뜹니다(`-p` 모드에서는 무시됨).

1. 터미널 1: 프로젝트 폴더에서 세션을 시작한다.
   ```
   claude --dangerously-load-development-channels server:lanmsg-p0
   ```
   경고 대화상자에서 **I am using this for local development**, 새 MCP 서버 승인 대화상자에서 **Use this MCP server**를 선택한다. 시작 배너 아래에 `Channels (experimental) messages from server:lanmsg-p0 inject directly in this session` 안내가 보이면 등록된 것이다.
2. 터미널 2: 응답 스트림을 연다.
   ```
   curl -N -H "Authorization: Bearer <토큰>" localhost:8788/events
   ```
3. 터미널 3: 메시지를 보낸다.
   ```
   curl -X POST -H "Authorization: Bearer <토큰>" -H "X-From: tester@pc-a" -d "ping: 지금 시각을 알려줘" localhost:8788
   ```
4. 기대 결과: 세션에 `← lanmsg-p0: ping: ...` 요약이 표시되고, Claude가 `reply` 도구를 호출해 터미널 2에 `Reply to 1: ...`이 나타난다. `reply` 호출 시 권한 확인이 뜰 수 있다.

문제가 생기면 세션에서 `/mcp`로 서버 상태를 보고, `claude --debug ...`로 시작해 `~/.claude/debug/<session-id>.txt`를 확인한다.

## P1로 넘어가기 전에 확인할 것

- 주입된 메시지가 도구 호출 사이에서 처리되는지, 세션이 idle일 때 새 턴이 시작되는지 관찰한다.
- 같은 PC에서 세션 두 개를 띄울 때 포트 충돌이 나는지 확인한다(`LANMSG_P0_PORT`로 회피 가능). P1의 bridge 데몬이 이 문제를 해결한다.
- 시스템 프롬프트(`instructions`)에 넣은 "신뢰할 수 없는 입력" 지시가 실제로 지켜지는지 확인한다(S-05).
